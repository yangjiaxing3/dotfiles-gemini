# Explain Like I Am... (ELI5 白話解釋技能)

> 來源：`DreambigOu/ELI5`（適配繁體中文與 `/ponytail` 多 Agent 協作規範）。
> 目標：把任何技術架構、程式碼變更、錯誤日誌或業務流程，精準翻譯成「目標對象一聽就懂」的人話。

## 核心四步驟

### 1. 先鎖定受眾（Identify Audience）
- 未明確指定對象時，預設以「**完全零技術背景的外行人**」為基準（經典 ELI5：短句、零行話、生活類比）。
- 若有指定對象（例如：老闆／營運主管、門市店長、設計師、工程師），依其關心重點調整切入點（完整分級與語氣矩陣見 `references/detailed-guide.md`）。

### 2. 先讀懂實情再翻譯（Read Source First）
- **禁止只憑檔名或猜測解釋**：必須先看過實際程式碼、錯誤訊息或流程文件，釐清「為什麼存在」與「實際怎麼運作」。

### 3. 四段式白話輸出（What → Analogy → Layers → So What）
1. **一句話破題（What）**：先講結論與核心用途，不堆前置鋪陳。
2. **生活類比（Analogy）**：用對方日常熟悉的場景比喻（例如：點餐櫃檯、倉庫理貨員、門禁磁扣）；非不得已出現專有名詞時，當場用括號白話註解。
3. **分層補細節（Layers）**：僅補充受眾需要知道的 2–4 個關鍵步驟；若涉及跨系統／多步驟流程，可搭配 `/diagram-design` 產出直覺圖解。
4. **影響與決策（So What）**：收尾講清楚「這件事解決了什麼問題、有什麼限制或風險、接下來誰要做什麼」。

### 4. 與 `/ponytail` 及多 Agent 協作（Ponytail × ELI5 模式）
- **分工原則**：`/ponytail` 負責讓程式碼極簡無贅肉；`/eli5` 負責把結果翻譯給人看，兩者不互相取代。
- **協作流程**：
  1. 實作與審查階段走 `/ponytail`（最小完整改動、保護核心演算法、`rule_lint` 檢查）。
  2. 在 **新功能上線說明、PR 摘要、跨 Agent 交接報告、SOP 教學或故障復盤** 時啟動 `/eli5`，把技術 diff 轉成老闆或門市人員秒懂的功能／風險說明。
  3. 遇到 `/ponytail` 留下的 `// shortcut:` 妥協時，直接用白話解釋「目前先這樣做省下什麼、上限在哪、未來何時要升級」。

## ⚠️ Gotchas (避坑指南)
- **🛑 嚴禁稀釋核心規格與數學精度**：撰寫或審查 3D 幾何算法、財務計價公式、IoT 校準參數、資安權限邊界與 API 欄位契約時，**不可**用模糊類比取代精確定義；必須「精確契約照寫，白話摘要另附」。
- **禁止居高臨下說教**：對外行人用親切生活比喻，但不能歪曲事實（寧取 80% 精準且聽得懂，不取 100% 艱澀卻看攏無）；對主管與營運端直接講影響、成本、風險與選項。
- **保留可追溯原文識別符**：解釋概念用純白話，但提及的檔案路徑、指令、API 端點或錯誤碼須保留英文原文，確保工程端可對照查證。
- **全繁體中文輸出**：除非使用者明確要求英文，所有說明、類比與標題一律使用自然繁體中文。
