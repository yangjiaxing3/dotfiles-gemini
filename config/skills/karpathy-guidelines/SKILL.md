# Karpathy-Inspired Coding Guidelines

當在專案中進行深層實作或重構時，請嚴格遵守以下由 Andrej Karpathy 觀察歸納出的防雷守則。這四點精神已深深整合至我們的 Multi-Agent Pipeline 中。

## 1. 思考優先 (Think Before Coding)
**不要預設立場。不要隱藏困惑。主動提出取捨 (Tradeoffs)。**
- **明確闡述假設**：如果你對需求或程式碼某段有疑慮，直接發問，不要盲猜。
- **提供多重解法**：如果任務有模糊空間，提供不同的實作路徑並分析優缺點。
- **敢於提出反對意見**：如果你發現了更簡單、安全的解法，應主動提出替換原本的複雜構想。
- **遇到困惑就暫停**：明確指出哪裡不懂，要求進一步澄清。

## 2. 極致極簡 (Simplicity First)
**寫出剛好解決問題的最少程式碼。不要過度推測未來需求。**
- 不加任何使用者沒要求的花俏功能。
- 不要為了「只有一種情況」的情境撰寫龐大的抽象類別或介面。
- 拒絕未經要求的「高彈性 (Configurability)」。
- 移除多餘的複雜防呆：如果不合理的情境根本不可能發生，就不要加上一堆 error handling。
- **終極指標**：如果 200 行才能解決的問題可以用 50 行更暴力的寫完，選 50 行的那種。

## 3. 外科手術式修改 (Surgical Changes)
**只碰你該碰的地方。只清理你自己製造的垃圾。**
- **嚴格範圍限制**：搭配 Graphify 知識圖譜，只允許在修改節點的第一層 (1-hop) 依賴邊界內變動代碼。
- **不要順手牽羊**：禁止借題發揮去「優化」周邊不相干的程式碼、註解或排版。
- **順從既有風格**：即使你覺得原本的寫法很醜，只要能運作，就無縫配合它。
- **清理孤兒代碼**：如果「你的修改」讓某些 Imports/Functions 變成了死代碼，請刪掉它們。但如果原本就有死代碼，只要不是你造成的，假裝沒看到。
- **終極指標**：每一行 diff 變動，都必須能 100% 回溯到使用者的直接需求。

## 4. 目標驅動執行 (Goal-Driven Execution)
**定義清楚的成功標準。自主驗證直到通過。**
將模糊的祈使句轉化為可驗證的目標：
- 「加上驗證」改成 $\rightarrow$ 「先寫一個不合法傳入會報錯的測試，然後把它修到過」。
- 「修 Bug」改成 $\rightarrow$ 「先寫一個能重現 bug 的腳本，然後把它改到亮綠燈」。
- 「重構這段」改成 $\rightarrow$ 「確保重構前後，所有相依模組與測試都依然正常運作」。
- 任務拆解必須寫出：`1. [步驟] -> 驗證: [預期結果]` 讓執行具備封閉的查證迴圈。

## ⚠️ Gotchas (避坑指南)
- **終端機輸出保護 (Context Overflow Prevention)**：執行腳本或查詢時，禁止直接將上百筆 JSON/日誌印到 stdout；請導向暫存檔或加上筆數限制。
- **零區防禦與 Port 禁令**：修改或執行指令前嚴守工作區邊界，嚴禁綁定或終止保留埠 (`8000`、`5100`、`3000`)。
